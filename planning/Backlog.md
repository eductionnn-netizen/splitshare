## SS-01 — Согласовать модель данных и API

**Исполнитель:** руководитель Backend; согласование с руководителем Frontend. **Даты:** 05.10–18.10.2026.

Описать Group, Member, Expense, ExpenseShare, Settlement; определить идентификаторы, связи,
JSON-схемы, правила доступа и формат ошибок. Использовать прототип как основу вычислений.

**Критерии приёмки:** опубликован контракт четырёх методов API из раздела «Архитектура»; есть примеры
успешных и ошибочных ответов; Frontend и QA согласовали контракт в карточке.

## SS-02 — Спроектировать основной пользовательский сценарий

**Исполнитель:** руководитель Frontend. **Даты:** 05.10–18.10.2026.

Подготовить макеты создания группы, ввода расхода, списка балансов и возврата долга.
Учесть пустые состояния, загрузку, неверную сумму и отсутствие доступа.

**Критерии приёмки:** сценарий трёх друзей показан от создания группы до расчёта;
поля согласованы с Backend; есть отображение сумм с двумя знаками после запятой.

## SS-03 — Реализовать хранение групп и расходов

**Исполнитель:** разработчик Backend. **Даты:** 19.10–01.11.2026.

Создавать группы и расходы через API, сохранять данные в базе, проверять, что пользователь входит в группу.

**Критерии приёмки:** данные сохраняются после перезапуска; неизвестный участник и отрицательная
сумма отклоняются; пользователь другой группы не читает и не изменяет расходы;
сценарии создания и отказа покрыты интеграционными тестами.

## SS-04 — Подключить расчёт долей и балансов к API

**Исполнитель:** разработчик Backend. **Даты:** 02.11–15.11.2026.

Подключить существующий модуль расчёта к API и передавать ему данные из хранилища.

**Критерии приёмки:** 100 копеек делятся на 34/33/33; сумма балансов равна нулю;
пример ужина и такси даёт +170000/−40000/−130000 коп.; контрактный тест проверяет API.

## SS-05 — Реализовать взаиморасчёты и подтверждение возврата

**Исполнитель:** разработчик Backend. **Даты:** 16.11–29.11.2026.

Выдавать предложения переводов и сохранять подтверждённые возвраты.
Определить, кто вправе подтверждать получение, и исключить повторную обработку одного запроса.

**Критерии приёмки:** предложения погашают все балансы; повтор с тем же ключом идемпотентности
не меняет баланс второй раз; подтверждение доступно только участникам соответствующего перевода;
задолженность меняется после подтверждения возврата.

## SS-06 — Реализовать формы группы и расходов

**Исполнитель:** разработчик Frontend. **Даты:** 16.11–29.11.2026.

Создать формы по макетам SS-02 и подключить API. До готовности серверной части
использовать тестовые ответы. Приёмку проводить после подключения работающего API.

**Критерии приёмки:** группа и расход создаются в браузере; есть выбор плательщика и получателей;
ошибка API показана рядом с полем; повторное нажатие во время отправки заблокировано;
сохранённый расход отражается в обновлённом балансе.

## SS-07 — Показать балансы и возврат долга в интерфейсе

**Исполнитель:** разработчик Frontend. **Даты:** 30.11–13.12.2026.

Показать «вам должны», «вы должны», список предложенных переводов и подтверждение возврата.

**Критерии приёмки:** для каждого долга правильно указаны отправитель и получатель; суммы совпадают с API;
подтверждение обновляет экран; нулевой баланс показывает «Вы рассчитались»;
при ошибке сохранения пользователь получает сообщение об ошибке.

## SS-08 — Подключить self-hosted runner и CI

**Исполнитель:** инженер DevOps. **Даты:** 05.10–18.10.2026.

Зарегистрировать локальный runner с меткой `splitshare-private` в отдельном приватном CI-репозитории; опубликовать подготовленный
workflow; обеспечить тестирование, сборку и запуск собранного приложения.

**Критерии приёмки:** есть ссылка на успешный запуск GitHub Actions и проверенный коммит; задание выполнено
на локальном runner; тесты прошли; `splitshare.pyz` запускается; артефакт доступен
для скачивания. При добавлении API включить в CI интеграционные тесты.

## SS-09 — Проверить сквозной сценарий и ошибки

**Исполнитель:** инженер по тестированию. **Даты:** 14.12–20.12.2026.

Проверить в браузере создание группы, два расхода, балансы и подтверждение возвратов.
Проверить некорректный ввод, отсутствие доступа, двойную отправку и перезапуск приложения.

**Критерии приёмки:** воспроизводимые тесты проходят на собранной версии; результат
содержит идентификатор проверенного коммита; найденные блокирующие дефекты исправлены и перепроверены.

## SS-10 — Подготовить выпуск приложения

**Исполнитель:** ответственный за выпуск; согласование с владельцем продукта. **Даты:** 21.12–27.12.2026.

Подготовить релиз, обновить Wiki и описание версии, проверить запуск приложения на примере группы из трёх участников.

**Критерии приёмки:** выпущена версия с воспроизводимой сборкой; есть ссылка на успешный CI;
приложение запущено локально; сценарий работает; ограничения версии перечислены;
wiki, доска и квартальный план соответствуют фактическому состоянию.
